# ADR-003: Arquitectura del Backend — Node.js, TypeScript y NestJS

## Metadatos
- **Identificador**: ADR-003
- **Título**: Adopción de Node.js, TypeScript y NestJS como Framework de Backend para el Monolito Modular
- **Estado**: APROBADO
- **Fecha de Aprobación**: 2026-10-01
- **Impacto en Baseline SRS / SAD de Análisis**: NINGUNO
- **Módulos Afectados**: MOD-01 a MOD-09
- **Requisitos Trazados**: RF-01 a RF-18, RNF-01 a RNF-09, RN-01 a RN-09, CU-01 a CU-30, CU-04.1

---

## 1. Contexto y Planteamiento del Problema
Habiendo establecido en ADR-001 que el estilo global de backend es el **Monolito Modular**, se requiere seleccionar el entorno de ejecución (runtime), lenguaje y framework de servidor para construir la lógica de negocio de TraceFlow SCM.
Los requisitos imponen:
- Implementación de 9 módulos lógicos altamente estructurados (MOD-01 a MOD-09).
- Cumplimiento de 9 reglas de negocio estrictas (RN-01 a RN-09), incluyendo segregación de funciones (SoD), validaciones criptográficas de integridad (SHA-256) y bloqueos de sincronización (Check-Out).
- Exposición de una API RESTful documentada (ADR-009).
- Alta mantenibilidad (RNF-08) y portabilidad basada en contenedores (RNF-07).

Adicionalmente, se debe rectificar y subsanar formalmente el uso de versiones obsoletas: **Node.js 18 LTS se encuentra oficialmente fuera de soporte (End-of-Life)**, por lo que debe adoptarse una versión con ciclo de vida plenamente activo.

---

## 2. Criterios de Evaluación y Requisitos Relevantes
1. **Soporte Nativo de Modularidad y Encapsulamiento**: Capacidad del framework para imponer límites modulares estrictos mediante inyección de dependencias y aislamiento de ámbitos, reflejando 1:1 los módulos MOD-01..09.
2. **Soporte Vigente del Runtime (Sin Obsolescencia)**: Selección de una versión LTS activa de Node.js con horizonte de soporte extendido (e.g. Node.js 24 LTS o versión LTS activa aprobada en la baseline de implementación).
3. **Unificación del Lenguaje Fullstack (TypeScript)**: Empleo de TypeScript tipado de extremo a extremo, facilitando la consistencia entre capas, DTOs compartidos y validaciones estáticas.
4. **Ecosistema y Seguridad**: Soporte robusto para librerías criptográficas estándar (módulo nativo `crypto` para SHA-256), manejo transaccional de base de datos, interceptores de auditoría y middleware de seguridad.
5. **No Exclusividad Dogmática**: No argumentar falazmente que NestJS es el "único" framework modular existente, sino justificar con rigor técnico por qué es la opción óptima seleccionada frente a sus alternativas.

---

## 3. Alternativas Consideradas

### Alternativa A: Node.js con Express o Fastify Puro (Sin Framework de Arquitectura)
- **Descripción**: Construir el servidor utilizando Express o Fastify directamente, organizando la estructura de carpetas de forma manual.
- **Ventajas**: Máxima ligereza, mínima abstracción, altísimo rendimiento bruto de I/O.
- **Desventajas**:
  - Carece de un sistema formal de inyección de dependencias (IoC/DI) e inversión de control out-of-the-box.
  - Alto riesgo de que el equipo desarrolle soluciones ad-hoc inconsistentes para la modularidad, acoplando controladores y servicios sin fronteras firmes.
  - Mayor esfuerzo de configuración para validaciones, OpenAPI/Swagger y manejo unificado de excepciones.
- **Veredicto**: RECHAZADA.

### Alternativa B: Stack Java / Spring Boot o C# / ASP.NET Core
- **Descripción**: Desarrollar el backend en frameworks empresariales fuertemente tipados sobre la JVM o .NET CLR.
- **Ventajas**: Excelente soporte de inyección de dependencias, transaccionalidad madura, ecosistema empresarial robusto.
- **Desventajas**:
  - Divergencia de lenguaje respecto al frontend (Java/C# vs TypeScript), impidiendo compartir esquemas de validación, interfaces de dominio o tipos comunes.
  - Mayor consumo de memoria base y tiempos de arranque más lentos en contenedores pequeños respecto a Node.js.
  - Sobrecarga de complejidad tecnológica para el equipo asignado al proyecto.
- **Veredicto**: RECHAZADA.

### Alternativa C: Node.js (LTS Soportada) + TypeScript + NestJS Framework — *SELECCIONADA*
- **Descripción**: Backend estructurado sobre NestJS ejecutado en Node.js LTS activa, empleando TypeScript en modo estricto. NestJS provee una arquitectura inspirada en Angular/Spring con módulos (`@Module`), controladores (`@Controller`), servicios (`@Injectable`), interceptores, filtros y guardas (`@CanActivate`).
- **Ventajas**:
  - Mapeo directo 1:1 entre los módulos lógicos del SAD de Análisis (MOD-01 a MOD-09) y los módulos de NestJS (`AuthModule`, `ProjectModule`, `ConfigItemModule`, `ChangeRequestModule`, `VersionControlModule`, `QaModule`, `BaselineModule`, `IncidentModule`, `AuditModule`).
  - Inyección de dependencias nativa y decoradores que facilitan la aplicación de Segregación de Funciones (SoD) y control de acceso (Guards RBAC).
  - Integración nativa con OpenAPI/Swagger (`@nestjs/swagger`) generando especificaciones 3.0 automáticamente a partir de DTOs decorados.
  - Validación declarativa de entradas mediante `class-validator` y `class-transformer` en Pipes de validación globales.
  - Excelente ecosistema para transaccionalidad relacional e integración de almacenamiento.
- **Desventajas**: Curva de aprendizaje moderada para desarrolladores no familiarizados con patrones de inyección de dependencias y decoradores TypeScript.
- **Veredicto**: APROBADA.

## 4. Decisión Aprobada y Justificación Técnica
Se aprueba formalmente la adopción de **Node.js (versión LTS activa soportada en la baseline de implementación, tomando como referencia inicial Node.js 24 LTS)**, **TypeScript** y el framework **NestJS** como base técnica del backend de TraceFlow SCM.

### Justificación Técnica:
1. **Resolución de Obsolescencia**: Se prohíbe el uso de Node.js 18 LTS por obsolescencia y fin de ciclo de vida. La baseline de implementación adoptará la versión Node.js LTS activa vigente (Node.js 24 LTS o la LTS soportada al congelar la baseline técnica).
2. **Encapsulamiento y Gobernanza Modular**: NestJS proporciona el contenedor de inversión de control (IoC) ideal para materializar las fronteras modulares de MOD-01 a MOD-09, asegurando que cada módulo exponga únicamente los servicios de exportación estrictamente autorizados.
3. **Gobernanza de Seguridad y SoD**: La combinación de NestJS Guards, Pipes e Interceptores permite centralizar de forma declarativa e inviolable:
   - Validación de roles RBAC en cada endpoint (`RN-01`, `RN-04`).
   - Verificación de Segregación de Funciones (`RN-05`), impidiendo que un implementador actúe como certificador de calidad.
   - Auditoría automática mediante interceptores globales que capturan usuario, timestamp, acción y payload para MOD-09 (`RN-02`).
4. **Cumplimiento de Integridad SHA-256**: Acceso nativo y de alto rendimiento al módulo criptográfico del runtime (`node:crypto`) para el cómputo y validación de hashes SHA-256 sobre artefactos de ECS (`RN-08`).

## 5. Consecuencias y Trade-offs
### Positivas:
- Arquitectura fuertemente tipada y estandarizada en todo el proyecto.
- Generación automática de contratos OpenAPI sincronizados con el código.
- Facilidad para escribir pruebas unitarias con Jest mocking de dependencias inyectadas.

### Negativas / Riesgos:
- Sobrecarga de clases, decoradores y abstracciones respecto a micro-frameworks más simples.
- Necesidad de controlar las importaciones circulares entre módulos de NestJS mediante `forwardRef()` o servicios de desacoplamiento por eventos.

---

## 6. Mitigaciones y Medidas Compensatorias
1. **Reglas de Arquitectura Modular**: Prohibir importaciones relativas directas entre carpetas de distintos módulos; la comunicación intermodular se realizará exclusivamente a través de los servicios exportados en el `@Module` correspondiente.
2. **Uso de Linters y Tipado Estricto**: Configuración de `tsconfig.json` con `"strict": true`, `"noImplicitAny": true` y `"exactOptionalPropertyTypes": true`.
3. **Monitoreo de Dependencias**: Auditoría automatizada de vulnerabilidades mediante `npm audit` o herramientas equivalentes en el pipeline de CI/CD.
