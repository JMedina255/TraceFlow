# ADR-004: Motor de Base de Datos Principal — PostgreSQL Relacional Transaccional

## Metadatos
- **Identificador**: ADR-004
- **Título**: Adopción de PostgreSQL como Motor de Base de Datos Relacional y Transaccional Principal
- **Estado**: APROBADO
- **Fecha de Aprobación**: 2026-10-01
- **Impacto en Baseline SRS / SAD de Análisis**: NINGUNO
- **Módulos Afectados**: MOD-01 a MOD-09 (Persistencia de todos los módulos del sistema)
- **Requisitos Trazados**: RF-01 a RF-18, RNF-01, RNF-02, RNF-03, RNF-06, RNF-08, RNF-09, RN-01 a RN-09

---

## 1. Contexto y Planteamiento del Problema
TraceFlow SCM requiere persistir la totalidad de las entidades de gobernanza y control de configuración del software: usuarios, roles, asignaciones de SoD, proyectos, ramas, elementos de configuración (ECS), metadatos de versiones, checksums SHA-256, solicitudes de cambio (RFC) en sus 14 estados canónicos, dictámenes del CCB, bloqueos de sincronización de Check-Out, registros de pruebas QA, líneas base congeladas, tickets de incidencias y pistas inmutables de auditoría forense.

El sistema impone requisitos críticos de integridad transaccional:
- **RN-06**: Bloqueo exclusivo de sincronización (un solo Check-Out activo por ECS a nivel de sistema).
- **RN-02**: Auditoría inmutable e inviolable de cada acción.
- **RN-07**: Trazabilidad bidireccional total entre Incidencias, RFCs, ECS, Versiones y Líneas Base.
- **RNF-06**: Consultas complejas de histórico y trazabilidad en tiempo $\le 3$ segundos.
- **RNF-09**: Respaldo transaccional periódico sin inconsistencias.

El problema arquitectónico consiste en seleccionar el motor de persistencia adecuado, separando con rigor conceptual la **Decisión Arquitectónica** (la elección del motor relacional PostgreSQL frente a alternativas) de la **Decisión de Implementación** (la versión específica de PostgreSQL a desplegar).

---

## 2. Criterios de Evaluación y Requisitos Relevantes
1. **Soporte ACID Estricto y Concurrencia**: Garantía de transacciones serializables o read-committed con mecanismos de aislamiento y bloqueo precisos para evitar condiciones de carrera en Check-Out concurrentes (RN-06).
2. **Índices Parciales / Condicionales Nativos**: Capacidad de definir restricciones únicas parciales en base de datos (e.g. `UNIQUE (ecs_id) WHERE status = 'LOCKED'`) para garantizar que la regla de negocio RN-06 sea inviolable incluso ante fallos de aplicación.
3. **Tipos de Datos Semiestructurados Indexables (JSONB)**: Capacidad para almacenar payloads de auditoría dinámicos, resultados de pruebas QA y manifiestos de línea base en formato estructurado indexable sin perder la rigidez relacional del núcleo.
4. **Separación de Niveles de Decisión**:
   - **Nivel Arquitectónico**: Selección de PostgreSQL como motor relacional transaccional unificado.
   - **Nivel de Implementación**: Selección de una versión con horizonte de soporte activo (LTS vigente, e.g. PostgreSQL 16 LTS o PostgreSQL 17 LTS, garantizando soporte de seguridad más allá de 2028-2029).
5. **Rendimiento e Indexación Avanzada (RNF-06)**: Índices B-Tree, Hash, GIN y GiST para garantizar que las consultas históricas de versiones de ECS y auditoría cumplan el umbral de $\le 3$ segundos.

## 3. Alternativas Consideradas

### Alternativa A: Motores NoSQL Orientados a Documentos (MongoDB / Couchbase)
- **Descripción**: Persistir todas las entidades como documentos JSON en colecciones NoSQL.
- **Ventajas**: Flexibilidad de esquema para metadatos variados de ECS y auditoría.
- **Desventajas**:
  - Falta de integridad referencial declarativa estricta entre RFCs, ECS, versiones, proyectos y usuarios.
  - Alto riesgo de corrupción de datos y pérdida de trazabilidad relacional (RN-07).
  - Las transacciones multi-documento en NoSQL presentan sobrecostos significativos de latencia y complejidad.
  - Imposibilidad de aplicar índices únicos condicionales nativos con la robustez requerida para RN-06.
- **Veredicto**: RECHAZADA.

### Alternativa B: Motor Relacional Alternativo (MySQL / MariaDB)
- **Descripción**: Emplear MySQL o MariaDB como motor de base de datos relacional.
- **Ventajas**: Muy extendido, fácil configuración y amplio soporte.
- **Desventajas**:
  - MySQL no soporta de forma nativa índices únicos parciales/condicionales (`WHERE`), obligando a recurrir a columnas generadas virtuales o triggers complejos para implementar la restricción de bloqueo exclusivo de RN-06.
  - Menor flexibilidad en el manejo de tipos JSONB y operadores de indexación avanzada GIN para registros de auditoría y metadatos de configuración.
  - Soporte de transacciones concurrentes con matices sutiles en niveles de aislamiento respecto al estándar ANSI SQL estricto de PostgreSQL.
- **Veredicto**: RECHAZADA.

### Alternativa C: PostgreSQL Relacional Transaccional — *SELECCIONADA*
- **Descripción**: Sistema de gestión de bases de datos relacional orientado a objetos de código abierto, con cumplimiento exhaustivo de estándares ACID, soporte nativo de índices condicionales parciales, columnas JSONB con índices GIN, funciones y triggers para auditoría, y herramientas maduras de respaldo transaccional (`pg_dump`, WAL archiving).
- **Ventajas**:
  - Soporte nativo de índices únicos parciales: permite modelar `RN-06` con una restricción única condicional a nivel de motor.
  - Potente soporte híbrido relacional + JSONB: las tablas críticas mantienen integridad referencial estricta, mientras que los payloads de auditoría y metadatos variables de ECS se almacenan en JSONB indexado.
  - Transaccionalidad robusta probada en entornos empresariales de misión crítica.
  - Excelente ecosistema de conexión con Node.js/NestJS (TypeORM / Prisma / Kysely / node-postgres nativo).
  - Soporte LTS prolongado garantizado por la PostgreSQL Global Development Group.
- **Desventajas**: Requiere configuración y afinamiento adecuado de memoria (`shared_buffers`, `work_mem`) y mantenimiento de estadísticas (`VACUUM`).
- **Veredicto**: APROBADA.

## 4. Decisión Aprobada y Justificación Técnica
Se aprueba formalmente la adopción de **PostgreSQL** como motor de base de datos relacional y transaccional principal de TraceFlow SCM.

### Distinción Formal de Decisiones:
- **Decisión Arquitectónica (Aprobada en este ADR)**: Elección de PostgreSQL como motor relacional transaccional unificado para MOD-01 a MOD-09.
- **Decisión de Implementación (Fijada para la Baseline Técnica)**: Adopción de **PostgreSQL 16 LTS** (o versión superior activa como PostgreSQL 17 LTS), garantizando soporte oficial activo de parches y seguridad hasta noviembre de 2028 o posterior.

### Justificación Técnica:
1. **Blindaje de la Regla de Negocio RN-06**: Permite crear una restricción única condicional sobre el elemento de configuración y su estado de bloqueo, asegurando a nivel de motor de datos que jamás existirán dos registros de bloqueo activo sobre el mismo ECS simultáneamente.
2. **Garantía de Integridad Referencial de Trazabilidad (RN-07)**: Claves foráneas y restricciones en cascada restrictivas impiden la eliminación de registros de configuración, cambios o incidencias que cuenten con trazabilidad histórica activa.
3. **Auditoría Estructurada de Alto Rendimiento (MOD-09, RN-02)**: Las columnas JSONB permiten registrar el delta exacto de los cambios de estado sin alterar el esquema relacional rígido, manteniendo índices GIN para cumplir con consultas de auditoría en tiempos $\le 3$ s (RNF-06).

---

## 5. Consecuencias y Trade-offs
### Positivas:
- Integridad ACID total y cumplimiento sin concesiones de las reglas de negocio críticas de SCM.
- Soporte nativo de características avanzadas de indexación y tipos semiestructurados.
- Herramientas estándar de la industria para administración, observabilidad y respaldos.

### Negativas / Riesgos:
- La base de datos se convierte en un punto central de persistencia que requiere dimensionamiento adecuado de conexiones y memoria.
- Requiere una estrategia coordinada de respaldo consistente con el almacenamiento físico externo de archivos de ECS (ver ADR-005 y ADR-010).

---

## 6. Mitigaciones y Medidas Compensatorias
1. **Pool de Conexiones**: Implementación de pooling de conexiones gestionado en NestJS (e.g. pool de `pg` / TypeORM) para optimizar la concurrencia y evitar el agotamiento de sockets.
2. **Indexación Estratégica**: Creación obligatoria de índices B-Tree sobre claves foráneas y columnas de filtrado frecuente (`rfc_id`, `ecs_id`, `version_id`, `project_id`, `created_at`) para garantizar tiempos de respuesta $\le 3$ s (RNF-06).
3. **Separación de Responsabilidades de Almacenamiento**: Los archivos físicos voluminosos de los ECS no se almacenarán como blobs en PostgreSQL, sino en almacenamiento externo especializado desacoplado (ADR-005).
