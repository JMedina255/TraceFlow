# ADR-009: Contratos de Comunicación API — RESTful, JSON y OpenAPI 3.0

## Metadatos
- **Identificador**: ADR-009
- **Título**: Adopción de API RESTful con Cargas Útiles JSON y Especificación Formal OpenAPI 3.0
- **Estado**: APROBADO
- **Fecha de Aprobación**: 2026-10-01
- **Impacto en Baseline SRS / SAD de Análisis**: NINGUNO
- **Módulos Afectados**: MOD-01 a MOD-09
- **Requisitos Trazados**: RF-01 a RF-18, RNF-05, RNF-06, RNF-07, RNF-08, RN-01 a RN-09, CU-01 a CU-30, CU-04.1

---

## 1. Contexto y Planteamiento del Problema
TraceFlow SCM requiere comunicar de forma estandarizada y desacoplada su cliente frontend SPA (ADR-002) con el backend monolítico modular NestJS (ADR-001, ADR-003).
La comunicación debe:
- Exponer operaciones para los 31 Casos de Uso del sistema (CU-01 a CU-30 y CU-04.1).
- Garantizar que los contratos de interfaz estén formalmente definidos, documentados e inspeccionables para permitir pruebas automatizadas y consumo por parte del frontend.
- Proporcionar manejo semántico de errores estandarizado.

El problema arquitectónico radica en seleccionar el protocolo y estándar de comunicación, y definir la regla de gobernanza que vincule los casos de uso con las operaciones técnicas, estableciendo taxativamente el carácter de los ejemplos contenidos en las decisiones de diseño.

---

## 2. Criterios de Evaluación y Requisitos Relevantes
1. **Regla de Gobernanza de Rutas y Operaciones (Mandatoria)**:
   - Toda ruta, verbo o esquema expuesto en este ADR se clasifica expresamente como:
     **EJEMPLO ILUSTRATIVO — NO CONTRATO DEFINITIVO**.
   - El catálogo formal y definitivo de operaciones de API se construirá y formalizará en el **SAD de Diseño**, derivándose mediante la cadena de trazabilidad estricta:
     $$\mathbf{RF} \longrightarrow \mathbf{CU} \longrightarrow \mathbf{Diagrama\ de\ Secuencia\ de\ Dise	ilde{n}o} \longrightarrow \mathbf{Operacicute{o}n\ API\ (Verbo\ /\ Ruta\ /\ DTO\ /\ Ccute{o}digos\ HTTP)}$$
2. **Estandarización y Adopción Universal**: Uso de estándares abiertos maduros de la industria para APIs web.
3. **Manejo Semántico de Estados y Conflictos**: Soporte para comunicar claramente el éxito (200, 201, 204), errores de validación (400), fallos de autenticación/autorización (401, 403), recursos no encontrados (404), y conflictos de concurrencia y bloqueo de sincronización `RN-06` (409 Conflict).
4. **Estructura Estándar de Errores**: Formato unificado de reporte de incidentes en API basado en RFC 7807 (Problem Details for HTTP APIs).
5. **Generación Automatizada de Documentación y Tipos**: Capacidad de sincronizar el código con contratos OpenAPI 3.0 para consumo del frontend.

## 3. Alternativas Consideradas

### Alternativa A: GraphQL
- **Descripción**: Exponer un único endpoint `/graphql` que permita al cliente consultar grafos arbitrarios de datos.
- **Ventajas**: Flexibilidad para solicitar campos exactos; excelente para interfaces complejas con muchas relaciones anidadas.
- **Desventajas**:
  - Complejidad innecesaria en el backend para la autorización granular basada en roles y reglas SoD (`RN-01`, `RN-05`).
  - Dificultad para aplicar rate limiting, cacheo HTTP estándar y manejo de códigos semánticos HTTP de conflicto (e.g. 409 Conflict para bloqueo de concurrencia RN-06).
  - Sobrecosto en desarrollo y mantenimiento de esquemas sin aportar beneficios tangibles a un flujo transaccional SCM orientado a comandos y estados.
- **Veredicto**: RECHAZADA.

### Alternativa B: gRPC / Protobuf para la Web
- **Descripción**: Utilizar llamadas a procedimiento remoto gRPC con serialización binaria Protocol Buffers.
- **Ventajas**: Máximo rendimiento y compresión binaria.
- **Desventajas**:
  - Requiere un proxy intermediario (e.g. Envoy) para traducir gRPC-Web en navegadores, agregando complejidad operacional injustificada.
  - Imposibilidad de inspeccionar payloads fácilmente en las herramientas de desarrollo del navegador.
- **Veredicto**: RECHAZADA.

### Alternativa C: RESTful API con JSON y Especificación OpenAPI 3.0 — *SELECCIONADA*
- **Descripción**: Arquitectura REST sobre HTTP/HTTPS utilizando JSON como formato de intercambio, organizada en recursos orientados al dominio, versionada en la URI (`/api/v1/...`) y documentada formalmente mediante OpenAPI 3.0 generada con decoradores NestJS Swagger.
- **Ventajas**:
  - Estándar universal de la industria, altamente familiar para cualquier desarrollador web.
  - Integración nativa con los códigos semánticos HTTP (e.g. `201 Created`, `400 Bad Request`, `401 Unauthorized`, `403 Forbidden`, `409 Conflict` para violaciones de bloqueo `RN-06`).
  - Capacidad de generar clientes TypeScript fuertemente tipados para el frontend mediante generadores basados en el esquema OpenAPI.
  - Soporte nativo para subida y descarga de archivos de ECS mediante flujos `multipart/form-data` y streaming binario.
- **Desventajas**: Mayor verbosidad de texto en comparación con formatos binarios (mitigada por compresión gzip/brotli estándar de HTTP).
- **Veredicto**: APROBADA.

## 4. Decisión Aprobada y Justificación Técnica
Se aprueba formalmente la adopción de una **API RESTful sobre HTTP/HTTPS**, con cargas útiles estructuradas en **JSON**, códigos semánticos HTTP estandarizados y contrato documental gobernado por **OpenAPI 3.0 (Swagger)**.

### 4.1 Principios de Diseño de la API
1. **Versionado Explícito en Ruta**: Todos los endpoints se prefijarán con `/api/v1/` para permitir una evolución ordenada sin romper contratos existentes.
2. **Estructura Estándar de Respuesta de Error (RFC 7807)**:
   ```json
   {
     "statusCode": 409,
     "error": "Conflict",
     "message": "Violación de RN-06: El ECS ya se encuentra bloqueado por la Orden ECN-2026-004.",
     "timestamp": "2026-10-01T15:30:00.000Z",
     "path": "/api/v1/config-items/ecs-101/check-out"
   }
   ```
3. **Mapeo Semántico de Códigos HTTP**:
   - `200 OK`: Consulta o mutación sincrónica exitosa con retorno de datos.
   - `201 Created`: Recurso creado exitosamente (RFC, ECS, Versión, Proyecto).
   - `204 No Content`: Mutación exitosa sin cuerpo de retorno (e.g. liberación de bloqueo).
   - `400 Bad Request`: Error de validación de sintaxis o campos en DTO.
   - `401 Unauthorized`: Falta de autenticación o sesión expirada (RNF-04).
   - `403 Forbidden`: Privilegios insuficientes (RN-01) o violación de SoD (RN-05).
   - `404 Not Found`: Recurso inexistente en el sistema.
   - `409 Conflict`: Conflicto de estado o bloqueo de concurrencia activo (RN-06).
   - `500 Internal Server Error`: Excepción de servidor no controlada.

## 5. Consecuencias y Trade-offs
### Positivas:
- Contratos de comunicación limpios, predecibles y universales.
- Documentación interactiva de la API accesible para el equipo mediante Swagger UI.
- Capacidad de verificar automáticamente la consistencia de tipos entre backend y frontend.

### Negativas / Riesgos:
- Riesgo de divergencia si los desarrolladores modifican los controladores sin actualizar los decoradores de Swagger (mitigado por la integración automática de NestJS).

---

## 6. Mitigaciones y Medidas Compensatorias
1. **Pipes Globales de Validación**: Uso de `ValidationPipe` en NestJS configurado con `whitelist: true`, `forbidNonWhitelisted: true` y `transform: true` para rechazar automáticamente cualquier payload malicioso o no tipado.
2. **Exportación Automatizada de Swagger JSON**: Generación del archivo `swagger.json` en tiempo de compilación para auditoría de cambios en la API mediante Git.
