# ADR-010: Estrategia de Empaquetado, Despliegue, Continuidad y Respaldo Operacional

## Metadatos
- **Identificador**: ADR-010
- **Título**: Estrategia de Contenerización Docker, Operación, Alta Disponibilidad y Respaldo de Unidad Lógica
- **Estado**: APROBADO
- **Fecha de Aprobación**: 2026-10-01
- **Impacto en Baseline SRS / SAD de Análisis**: NINGUNO
- **Módulos Afectados**: Transversal a toda la infraestructura de TraceFlow SCM (MOD-01 a MOD-09)
- **Requisitos Trazados**: RNF-01 (Fiabilidad), RNF-02 (Disponibilidad 99.9%), RNF-07 (Portabilidad), RNF-08 (Mantenibilidad), RNF-09 (Respaldo Periódico Transaccional)

---

## 1. Contexto y Planteamiento del Problema
TraceFlow SCM requiere una estrategia de empaquetado y ejecución que permita desplegar el sistema de forma consistente, portátil y reproducible en entornos de desarrollo, pruebas y producción empresarial (RNF-07).
Asimismo, los requisitos no funcionales establecen metas rigurosas:
- **RNF-02 (Disponibilidad)**: Disponibilidad del sistema de al menos un 99.9 % en horario operativo.
- **RNF-08 (Mantenibilidad)**: Facilidad para actualizar componentes con mínimo impacto en el servicio.
- **RNF-09 (Respaldo Transaccional Periódico)**: Ejecución de respaldos que garanticen la recuperabilidad íntegra del sistema ante fallos mayores.

Adicionalmente, se detectó una **inconsistencia crítica en propuestas previas** que debe subsanarse de manera obligatoria:
- El diseño anterior únicamente respaldaba la base de datos PostgreSQL mediante `pg_dump`, omitiendo el almacenamiento físico de los ECS que reside fuera de la base de datos (ADR-005).
- Docker Compose por sí solo se ejecutaba como servicio monolítico en un único host, lo que hacía imposible garantizar matemáticamente un 99.9 % de disponibilidad ante fallas físicas de hardware.

El problema consiste en definir una arquitectura operativa realista y robusta que empaquete el sistema, establezca una estrategia concreta para alta disponibilidad y resuelva la unidad lógica de respaldo consistente.

---

## 2. Criterios de Evaluación y Requisitos Relevantes
1. **Sobriedad y Rigor Operativo en Disponibilidad (RNF-02)**:
   - Se ELIMINA y PROHÍBE la afirmación de que "Docker Compose por sí solo garantiza un 99.9 % de uptime o cero downtime".
   - Se establece una arquitectura de mitigación para despliegues en host único: instancias backend stateless detrás de un reverse proxy (Nginx), sondeos de salud (*health checks*), reinicios controlados (*rolling/blue-green restarts*) y volumen persistente de base de datos.
   - Se declara explícitamente el **riesgo de fallo catastrófico de hardware del host** y su estrategia de recuperación ante desastres (Disaster Recovery).
2. **Corrección Obligatoria de la Unidad Lógica de Respaldo (RNF-09)**:
   - Definición formal de la **Unidad Lógica de Respaldo**:
     $$\mathbf{Backup\ TraceFlow} = \mathbf{Snapshot\ DB} + \mathbf{Snapshot\ Storage} + \mathbf{Manifest}$$
   - El respaldo debe abarcar obligatoriamente:
     A. Base de datos PostgreSQL (`pg_dump` transaccional consistente).
     B. Contenido físico de los ECS custodiados (`/storage/`).
     C. Manifiesto de versiones y metadatos con timestamps de corte.
     D. Checksums criptográficos SHA-256 de verificación.
     E. Correspondencia consistente entre registros de base de datos y archivos físicos.
3. **Clasificación Formal de Parámetros Operativos**:
   - Parámetros específicos como horarios de ejecución (e.g. 02:00 AM) o políticas de retención histórica (e.g. 30 días) se definen expresamente como:
     **DECISIONES OPERATIVAS DE DISEÑO, no como exigencias funcionales de RNF-09**.
4. **Portabilidad y Desacoplamiento de Entorno (RNF-07)**: Empaquetamiento en imágenes de contenedor reproducibles mediante construcción multi-etapa (*multi-stage builds*).

## 3. Alternativas Consideradas

### Alternativa A: Despliegue Nativo "Bare-Metal" Sin Contenedores
- **Descripción**: Instalar Node.js, dependencias npm, PostgreSQL y Nginx directamente sobre el sistema operativo host.
- **Ventajas**: Máximo aprovechamiento de recursos de CPU y memoria sin capas de virtualización ligera.
- **Desventajas**:
  - Alta propensión al síndrome "funciona en mi máquina" debido a diferencias de versiones de SO, librerías compartidas y configuraciones locales.
  - Muy difícil de actualizar de forma limpia y automatizada (viola RNF-07 y RNF-08).
  - Complejidad en la replicación idéntica de entornos de pruebas y producción.
- **Veredicto**: RECHAZADA.

### Alternativa B: Clúster Completo Kubernetes (K8s) desde el Inicio
- **Descripción**: Desplegar TraceFlow SCM en un clúster multi-nodo orquestado por Kubernetes con mallas de servicios y operadores avanzados.
- **Ventajas**: Alta disponibilidad física nativa real con auto-failover entre nodos y balanceo distribuido.
- **Desventajas**:
  - Sobrecosto masivo de infraestructura, personal especializado y tiempo de administración.
  - Complejidad desmedida para la escala inicial del proyecto.
- **Veredicto**: DIFERIDA (Ruta de evolución futura viable si el cliente dispone de infraestructura multi-nodo).

### Alternativa C: Contenedores Docker Multi-Stage con Orquestación por Composición y Proxy Inverso — *SELECCIONADA*
- **Descripción**: Empaquetar el frontend SPA y el backend NestJS en contenedores Docker independientes utilizando compilación multi-etapa para minimizar el tamaño de las imágenes. Orquestar la topología inicial mediante Docker Compose estructurado con un reverse proxy Nginx al frente, múltiples réplicas stateless del backend, PostgreSQL transaccional sobre volumen persistente y un contenedor auxiliar de respaldo coordinado.
- **Ventajas**:
  - Portabilidad total (RNF-07): el sistema se levanta idénticamente en cualquier entorno compatible con Docker Engine.
  - Despliegues continuos con mínimo tiempo de inactividad mediante reinicios escalonados de réplicas detrás del proxy.
  - Simplicidad operativa ajustada a la escala del proyecto, con una vía de migración inmediata a Docker Swarm o Kubernetes en el futuro.
- **Desventajas**: En un host único físico, la caída del hardware interrumpe el servicio hasta que se restaure en un nuevo host.
- **Veredicto**: APROBADA.

## 4. Decisión Aprobada y Justificación Técnica
Se aprueba formalmente la adopción de **Contenedores Docker Multi-Stage** y **Docker Compose estructurado con Proxy Inverso Nginx y Respaldo de Unidad Lógica** como estrategia de empaquetado, despliegue y operación de TraceFlow SCM.

### 4.1 Topología de Despliegue Aprobada
La topología lógica se compone de los siguientes servicios:
1. **`proxy` (Nginx)**: Punto único de entrada HTTP/HTTPS. Termina SSL/TLS, sirve los activos estáticos del frontend React SPA (ADR-002), enruta las llamadas `/api/...` hacia el backend y balancea la carga entre réplicas del servicio backend.
2. **`backend` (NestJS - Múltiples Réplicas Stateless)**: 2 réplicas del contenedor de backend ejecutándose en paralelo. Al ser completamente stateless (las sesiones residen en base de datos - ADR-006), el proxy puede balancear peticiones sin estado pegajoso (*sticky sessions*).
3. **`database` (PostgreSQL)**: Contenedor con PostgreSQL 16+ LTS sobre un volumen persistente dedicado (`tf_pg_data`), configurado para durabilidad transaccional.
4. **`storage` (Volumen de Custodia ECS)**: Volumen montado persistente (`tf_ecs_storage`) gestionado por `LocalStorageAdapter` (ADR-005).
5. **`backup_worker` (Servicio de Respaldo)**: Proceso automatizado que ejecuta la rutina de respaldo consistente de la Unidad Lógica de Respaldo.

### 4.2 Estrategia para RNF-02 (Disponibilidad) y RNF-08 (Mantenibilidad)
Para mitigar interrupciones y acercarse al objetivo de RNF-02 en infraestructura de host único:
1. **Sondeos de Salud (*Health Checks*)**:
   - Cada contenedor implementa un endpoint `/health/liveness` y `/health/readiness`.
   - Docker monitorea la salud del proceso; si una réplica del backend falla, se reinicia automáticamente sin afectar a la réplica hermana.
2. **Despliegues con Cero Inactividad de Software (*Zero-Downtime Rolling Update*)**:
   - Para aplicar actualizaciones de software: se levanta una nueva réplica con la versión actualizada; Nginx redirige el tráfico hacia la nueva réplica una vez que su health check responde `200 OK`; luego se destruye la réplica anterior.
3. **Declaración Explícita de Riesgo de Hardware**:
   - En una topología de host único, un fallo físico catastrófico del servidor (e.g. fallo de placa base o disco físico no RAID) detendrá temporalmente el sistema. La mitigación para este escenario descansa en el **Procedimiento de Recuperación ante Desastres (DR)** mediante la restauración de la Unidad Lógica de Respaldo en un nuevo servidor host en un tiempo de recuperación objetivo (RTO $\le 2$ horas).

## 5. Especificación Obligatoria de Respaldo (RNF-09)
Se subsana la deficiencia de versiones previas formalizando la **Unidad Lógica de Respaldo**:

$$\mathbf{Backup\ TraceFlow} = \mathbf{Snapshot\ DB} + \mathbf{Snapshot\ Storage} + \mathbf{Manifest}$$

### 5.1 Protocolo del Backup Diario Consistente
El servicio `backup_worker` ejecuta diariamente el siguiente flujo automatizado:
1. **Fase 1 (Inicio y Ventana de Respaldo)**: Se registra en el log de auditoría el inicio del proceso de respaldo.
2. **Fase 2 (Respaldo Transaccional de PostgreSQL)**: Se ejecuta `pg_dump` con opciones transaccionales consistentes (`--format=custom --clean --if-exists`), generando un archivo de snapshot de base de datos (`db_snapshot_{timestamp}.dump`).
3. **Fase 3 (Snapshot de Almacenamiento Físico de ECS)**: Se realiza una copia snapshot o empaquetado comprimido del volumen físico de almacenamiento de artefactos (`tf_ecs_storage`), asegurando que todos los archivos promovidos a custodia definitiva queden capturados (`storage_snapshot_{timestamp}.tar.gz`).
4. **Fase 4 (Generación de Manifiesto y Checksum Cruzado)**:
   - Se calcula el hash SHA-256 del archivo `db_snapshot_{timestamp}.dump`.
   - Se calcula el hash SHA-256 del archivo `storage_snapshot_{timestamp}.tar.gz`.
   - Se genera un archivo de metadatos `manifest_{timestamp}.json` que vincula ambos snapshots, su marca temporal, versión del sistema y sus respectivos hashes.
5. **Fase 5 (Empaquetado y Verificación)**: La unidad completa (dump + storage tar + manifest) se consolida en el archivo de paquete maestro `traceflow_backup_{timestamp}.pkg`.
6. **Fase 6 (Destino y Retención)**: El paquete se transfiere a un almacenamiento secundario externo o aislado del disco principal.

### 5.2 Decisiones Operativas de Diseño (No Requisitos de SRS)
- **Horario de Ejecución**: Se define como **decisión operativa de diseño** la ejecución diaria a las **02:00 AM (hora local)**, seleccionada por corresponder al periodo de menor actividad del sistema.
- **Política de Retención**: Se define como **decisión operativa de diseño** una retención de **30 días para respaldos diarios** y **12 meses para respaldos mensuales de fin de ciclo**.

## 6. Consecuencias y Trade-offs
### Positivas:
- Respaldo 100% consistente que garantiza la recuperación simultánea de metadatos y contenido físico sin artefactos huérfanos.
- Despliegue portátil y homogéneo en cualquier servidor corporativo.
- Mitigación de caídas de software mediante réplicas y sondeos de salud automáticos.

### Negativas / Riesgos:
- La sincronización entre el volcado de base de datos y la copia del almacenamiento requiere que el volumen de almacenamiento se copie en una ventana temporal estrecha para evitar inconsistencias durante escrituras concurrentes.

---

## 7. Mitigaciones y Medidas Compensatorias
1. **Pruebas Periódicas de Restauración (Drill de Recuperación)**: Ejecución trimestral automatizada de restauración del backup en un entorno aislado para certificar la integridad del procedimiento.
2. **Monitoreo de Espacio en Disco**: Alertas automatizadas cuando el espacio en el volumen de backups o en el almacenamiento de ECS supere el 80% de ocupación.
