# ADR-011: Arquitectura de Inicialización, Organización Multiproyecto y Salvaguarda de Integración GitHub

## Metadatos

- **Título**: Arquitectura de Gobernanza Multiorganización, Asistente Híbrido de Inicialización y Salvaguarda Obligatoria de Integración GitHub
- **Estado**: PROPUESTO (Pendiente de Aprobación por el Responsable / CCB)

## 1. Contexto y Planteamiento del Problema

Hasta la línea base `master @ 99cf70f` (Etapa 07R / INT-01), **TraceFlow SCM** operaba bajo un modelo donde los proyectos (`PRJ-001`..`PRJ-003`) se asumían preexistentes en la base de datos dentro de una única organización implícita (`ÉXODO S.A.C.` representada únicamente como una columna textual `VARCHAR(120)` en `app_user`).

Asimismo, el ciclo de vida del proyecto permitía que un proyecto en estado `ACTIVE` iniciara operaciones SCM (como la creación de Solicitudes de Cambio `CU-04` o la custodia de Elementos de Configuración `CU-09..12`) sin contar con un repositorio de código fuente real enlazado, configurado o validado. Esta situación generaba las siguientes debilidades arquitectónicas:

1. **Ausencia de Tenant Raíz Formal (DA-02):** No existía una entidad relacional `organization` que agrupara proyectos, gestionara la membresía institucional ni aislara datos entre diferentes personas jurídicas o divisiones corporativas.
2. **Falta de Proceso Gradual de Inicialización (DA-05):** El caso de uso histórico `CU-02` presuponía una creación inmediata en un solo formulario, pasando directamente de `Inexistente` a `Activo`, sin capacidad de guardado borrador, configuración de metodología ni definición de fases.
3. **Desconexión con el Repositorio de Control de Versiones (DA-03, DA-04):** No existía un puente entre TraceFlow SCM y GitHub. La gestión de configuración de software requiere que los ítems de configuración (`ECS`) estén respaldados por repositorios físicos de código.
4. **Vulnerabilidad de Aprovisionamiento No Autorizado (DA-06):** No existía una salvaguarda estricta que impidiera invitar o asignar a proyectos a usuarios externos no registrados ni validados previamente por la organización.
5. **Riesgo de Operaciones Huérfanas:** Un usuario podía emitir RFCs sobre proyectos incompletos o sin respaldo en Git, violando el principio fundamental de control de configuración (IEEE 828).

## 2. Decisión Arquitectónica

Se aprueba formalmente el diseño de la arquitectura para la etapa de inicialización y gobierno multiproyecto bajo los siguientes principios:

### 2.1 Modelo Multitenant de Dos Niveles (DA-01, DA-02)
- Se incorpora la entidad raíz `traceflow.organization` como límite superior de gobernanza administrativa.
- Cada proyecto (`traceflow.project`) pertenece obligatoriamente a exactamente una organización (`organization_id UUID NOT NULL`).
- El acceso y visibilidad se gobiernan por dos niveles de membresía:
  1. **Membresía Organizacional (`organization_member`):** Define si un usuario pertenece a la entidad institucional y su rol administrativo (`OWNER`, `ADMIN`, `MEMBER`, `AUDITOR`).
  2. **Asignación por Proyecto (`user_project_assignment` / `project_team_role`):** Delimita el acceso operacional a los proyectos específicos de la organización y el rol funcional asignado (`PU-01`..`PU-07`).

### 2.2 Política Estricta de Incorporación de Miembros (DA-06)
- Queda prohibida la invitación de usuarios mediante enlaces públicos o direcciones de correo no registradas.
- La incorporación de integrantes a un proyecto se restringe exclusivamente a usuarios que ya cuenten con cuenta activa (`app_user.status = 'ACTIVE'`) y membresía vigente en la organización propietaria (`organization_member.status = 'ACTIVE'`).

### 2.3 Experiencia Híbrida: Asistente Inicial y Panel de Configuración Posterior (DA-05)
- **Asistente Inicial (Wizard):** Flujo guiado de 5 pasos para la concepción del proyecto:
  - Paso 1: Identidad, Objetivos y Alcance (`project_setup.identity_completed`).
  - Paso 2: Equipo y Asignación de Roles por Proyecto (`project_setup.team_completed`).
  - Paso 3: Metodología, Fases y Cronograma (`project_setup.methodology_completed`).
  - Paso 4: Integración GitHub (Vinculación o Creación) (`project_setup.github_completed`).
  - Paso 5: Resumen, Auditoría y Activación.
- **Persistencia Parcial y Autosave:** La entidad `project_setup` almacena el paso activo (`wizard_step`) y el payload temporal en un campo `JSONB draft_payload`, permitiendo abandonar y reanudar la inicialización sin corromper el modelo relacional.
- **Panel de Configuración Posterior:** Una vez activado el proyecto, el Gestor (`PU-02`) puede ajustar parámetros, ampliar cronogramas, reasignar miembros o actualizar webhooks desde una interfaz de pestañas tabulares dedicada (`/projects/:id/settings`).

### 2.4 Integración GitHub Híbrida y Segura (DA-03, DA-04)
- **Modalidades Soportadas (DA-03):**
  1. *Vinculación de Repositorio Existente:* Permite seleccionar un repositorio accesible del usuario u organización GitHub, validando permisos de administración o escritura.
  2. *Creación de Nuevo Repositorio:* Permite aprovisionar un nuevo repositorio (público o privado) en una organización o cuenta personal autorizada, inicializando la rama principal (`main`) y ramas canónicas de trabajo (`develop`, `staging`).
- **Arquitectura de Autenticación GitHub:** Se selecciona el modelo **GitHub App** como mecanismo primario institucional, complementado con OAuth App para repositorios personales autorizados:
  - Las credenciales se intercambian por Installation Access Tokens de corta duración (1 hora) generados bajo demanda.
  - Los secretos de webhooks y tokens de respaldo se cifran en reposo utilizando **AES-256-GCM** en `github_integration.encrypted_access_token` con vector de inicialización (`token_iv`) y etiqueta de autenticación (`token_auth_tag`).
- **Validación de Webhooks:** Todo webhook entrante en `/api/v1/projects/:id/github/webhook` se valida mediante HMAC-SHA256 contra la cabecera `X-Hub-Signature-256`. Las entregas se registran de forma idempotente en `github_event` utilizando `X-GitHub-Delivery`.

### 2.5 Salvaguarda SCM de Activación Obligatoria (DA-04)
- Se establece la regla `RN-12`: Ningún proyecto puede transicionar al estado `ACTIVO` si `github_integration.validation_status != 'VALIDATED'`.
- Se implementa el guardián de backend `ProjectActiveGuard` y la regla `RN-13`: Todos los controladores de procesos SCM (`RfcsController`, `ChangeOrdersController`, `ConfigItemsController`, `BaselinesController`) verifican que el proyecto referenciado se encuentre en estado `ACTIVO`.
- Todo intento de operar procesos SCM en proyectos en estado `BORRADOR`, `EN_CONFIGURACION`, `PENDIENTE_VALIDACION`, `SUSPENDIDO` o `ARCHIVADO` es rechazado formalmente con código **HTTP 412 Precondition Failed** o **HTTP 403 Forbidden**.

### 2.6 Transición de Proyectos Históricos
- Los proyectos históricos (`PRJ-001`, `PRJ-002`, `PRJ-003`) se asignan a la organización por defecto `ÉXODO S.A.C.` (`ORG-001`).
- Su estado se migra a `HISTORICO_PENDIENTE_GITHUB`.
- Las consultas históricas sobre RFCs y ECS permanecen plenamente operativas (modo lectura), pero cualquier intento de mutación SCM (crear nueva RFC, emitir ECN, hacer Check-In) requerirá completar la regularización de la integración GitHub (DA-04).

## 3. Consecuencias y Compensaciones

### Consecuencias Positivas
- **Aislamiento Multitenant Robusto:** Las organizaciones operan de forma segregada; no hay fuga de datos de proyectos entre clientes distintos de ÉXODO S.A.C.
- **Trazabilidad Completa del Código:** Todo cambio tramitado en TraceFlow SCM cuenta con respaldo directo en un repositorio Git verificable.
- **Experiencia de Usuario Guiada:** El asistente previene errores de configuración y permite planificar metodológicamente antes de iniciar el desarrollo.
- **Seguridad Criptográfica:** Cero credenciales expuestas en frontend, bitácora de auditoría ni repositorio de código.
- **Compatibilidad con Código Preexistente:** Se preservan las 21 tablas actuales y las APIs operativas sin interrupción destructiva.

### Consecuencias Negativas / Compensaciones
- **Dependencia de Conectividad Externa:** La activación del proyecto requiere conectividad saliente hacia la API de GitHub (`api.github.com`).
- **Complejidad Adicional de Permisos:** Se debe mantener la coherencia entre el rol institucional (`organization_member`), el rol canónico de seguridad (`PU-01`..`PU-07`) y la asignación en el proyecto.
