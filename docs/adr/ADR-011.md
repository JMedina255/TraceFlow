## 1. Contexto y Planteamiento del Problema

Hasta la línea base `master @ 99cf70f` (Etapa 07R / INT-01), **TraceFlow SCM** operaba bajo un modelo donde los proyectos (`PRJ-001`..`PRJ-003`) se asumían preexistentes en la base de datos dentro de una única organización implícita (`ÉXODO S.A.C.` representada únicamente como una columna textual `VARCHAR(120)` en `app_user`).

Asimismo, el ciclo de vida del proyecto permitía que un proyecto en estado `ACTIVE` iniciara operaciones SCM (como la creación de Solicitudes de Cambio `CU-04` o la custodia de Elementos de Configuración `CU-09..12`) sin contar con un repositorio de código fuente real enlazado, configurado o validado. Esta situación generaba las siguientes debilidades arquitectónicas:

1. **Ausencia de Tenant Raíz Formal (DA-02):** No existía una entidad relacional `organization` que agrupara proyectos, gestionara la membresía institucional ni aislara datos entre diferentes personas jurídicas o divisiones corporativas.
2. **Falta de Proceso Gradual de Inicialización (DA-05):** El caso de uso histórico `CU-02` presuponía una creación inmediata en un solo formulario, pasando directamente de `Inexistente` a `Activo`, sin capacidad de guardado borrador, configuración de metodología ni definición de fases.
3. **Desconexión con el Repositorio de Control de Versiones (DA-03, DA-04):** No existía un puente entre TraceFlow SCM y GitHub. La gestión de configuración de software requiere que los ítems de configuración (`ECS`) estén respaldados por repositorios físicos de código.
4. **Vulnerabilidad de Aprovisionamiento No Autorizado (DA-06):** No existía una salvaguarda estricta que impidiera invitar o asignar a proyectos a usuarios externos no registrados ni validados previamente por la organización.
5. **Riesgo de Operaciones Huérfanas:** Un usuario podía emitir RFCs sobre proyectos incompletos o sin respaldo en Git, violando el principio fundamental de control de configuración (IEEE 828).

## 2. Decisión Arquitectónica Propuesta

Se propone formalmente el diseño de la arquitectura para la etapa de inicialización y gobierno multiproyecto bajo los siguientes principios:

### 2.1 Modelo Multitenant de Dos Niveles (DA-01, DA-02)
- Se incorpora la entidad raíz `traceflow.organization` como límite superior de gobernanza administrativa.
- Cada proyecto (`traceflow.project`) pertenece obligatoriamente a exactamente una organización (`organization_id UUID NOT NULL`).
- El acceso y visibilidad se gobiernan por dos niveles de membresía:
  1. **Membresía Organizacional (`organization_member`):** Define si un usuario pertenece a la entidad institucional y su rol administrativo (`OWNER`, `ADMIN`, `MEMBER`, `AUDITOR`).
  2. **Asignación por Proyecto (`user_project_assignment` / `project_team_role`):** Delimita el acceso operacional a los proyectos específicos de la organización y el rol funcional asignado (`PU-01`..`PU-07`).

### 2.2 Política Estricta de Incorporación de Miembros (DA-06)
- Queda prohibida la invitación de usuarios mediante enlaces públicos o direcciones de correo no registradas (se elimina el estado `INVITED`).
- La incorporación de integrantes a un proyecto se restringe exclusivamente a usuarios que ya cuenten con cuenta activa (`app_user.status = 'ACTIVE'`) y membresía vigente en la organización propietaria (`organization_member.status = 'ACTIVE'`).
- La integridad se blinda en PostgreSQL mediante el disparador PL/pgSQL `enforce_project_member_organization_integrity`.

### 2.3 Experiencia Híbrida: Asistente Inicial y Panel de Configuración Posterior (DA-05)
- **Asistente Inicial (Wizard):** Flujo guiado de 5 pasos para la concepción del proyecto:
  - Paso 1: Identidad, Objetivos y Alcance (`project_setup.identity_completed`).
  - Paso 2: Equipo y Asignación de Roles por Proyecto (`project_setup.team_completed`).
  - Paso 3: Metodología, Fases y Cronograma (`project_setup.methodology_completed`).
  - Paso 4: Integración GitHub (Vinculación o Creación) (`project_setup.github_completed`).
  - Paso 5: Resumen, Auditoría y Activación.
- **Persistencia Parcial y Autosave:** La entidad `project_setup` almacena el paso activo (`wizard_step`) y el payload temporal en un campo `JSONB draft_payload`, permitiendo abandonar y reanudar la inicialización sin corromper el modelo relacional.
- **Panel de Configuración Posterior:** Una vez activado el proyecto, el Gestor (`PU-02`) puede ajustar parámetros, ampliar cronogramas, reasignar miembros o actualizar webhooks desde una interfaz de pestañas tabulares dedicada (`/projects/:id/settings`).

### 2.4 Integración GitHub Híbrida y Segura (DA-03, DA-04)
- **Modalidades Soportadas (DA-03):**
  1. *Vinculación de Repositorio Existente:* Permite seleccionar un repositorio accesible del usuario u organización GitHub, validando permisos de administración o lectura/escritura.
  2. *Creación de Nuevo Repositorio:* Permite aprovisionar un nuevo repositorio (público o privado) en una organización o cuenta personal autorizada, inicializando la rama principal (`main`) y ramas canónicas de trabajo (`develop`, `staging`).
- **Arquitectura de Autenticación GitHub y Tokens Bajo Demanda:**
  - Se selecciona el modelo **GitHub App** como mecanismo primario institucional, complementado con OAuth App para repositorios personales autorizados.
  - **Cero almacenamiento de tokens temporales en BD:** Los Installation Access Tokens de corta duración (1 hora) se generan en memoria bajo demanda mediante JSON Web Tokens (RS256) firmados con la clave privada asimétrica institucional (`.pem`) y se almacenan exclusivamente en un caché en memoria con TTL de 50 minutos.
  - En la base de datos solo se persiste el `installation_id` público, y de forma opcional `encrypted_oauth_token` (cifrado con AES-256-GCM) para cuentas personales de usuario.
  - Los secretos de webhooks se cifran en reposo utilizando **AES-256-GCM** en `github_integration.encrypted_webhook_secret` con vector de inicialización (`webhook_iv`) y etiqueta de autenticación (`webhook_auth_tag`).
- **Validación de Webhooks:** Todo webhook entrante en `/api/v1/projects/:id/github/webhook` se valida mediante HMAC-SHA256 contra la cabecera `X-Hub-Signature-256` utilizando comparación en tiempo constante (`crypto.timingSafeEqual`). Las entregas se registran de forma idempotente en `github_event` utilizando `X-GitHub-Delivery`.

### 2.5 Salvaguarda SCM de Activación Obligatoria (DA-04)
- Se establece la regla `RN-12`: Ningún proyecto puede transicionar al estado `ACTIVO` si `github_integration.validation_status != 'VALIDATED'`.
- Se implementa el guardián de backend `ProjectActiveGuard` y la regla `RN-13`: Todos los controladores de procesos SCM (`RfcsController`, `ChangeOrdersController`, `ConfigItemsController`, `BaselinesController`) verifican que el proyecto referenciado se encuentre en estado `ACTIVO`.
- Todo intento de operar procesos SCM en proyectos en estado `BORRADOR`, `EN_CONFIGURACION`, `PENDIENTE_VALIDACION`, `SUSPENDIDO`, `ARCHIVADO` o `HISTORICO_PENDIENTE_GITHUB` es rechazado formalmente con código **HTTP 412 Precondition Failed** o **HTTP 403 Forbidden**.

### 2.6 Política Estricta de Regularización de Proyectos Históricos
- Los proyectos históricos (`PRJ-001`, `PRJ-002`, `PRJ-003`) se asignan a la organización por defecto `ÉXODO S.A.C.` (`ORG-001`) con estado transitorio `HISTORICO_PENDIENTE_GITHUB`.
- **Prohibición de vinculación masiva a TraceFlow:** Queda terminantemente descartado asociar los proyectos históricos al repositorio de la plataforma TraceFlow. Cada proyecto cliente representa un sistema autónomo y debe vincularse de forma individual y explícita a su propio repositorio remoto por acción del Gestor (`PU-02`).
- Las consultas históricas sobre RFCs y ECS permanecen plenamente operativas (modo lectura), pero cualquier intento de mutación SCM (crear nueva RFC, emitir ECN, hacer Check-In) requerirá completar la regularización de la integración GitHub (DA-04).
- Cero scripts automáticos ni mutaciones artificiales de datos en la base de datos real.

### 2.7 Mínimo Privilegio e Integridad Referencial en Base de Datos
- **Restricción de Cascada:** Se sustituye `ON DELETE CASCADE` por `ON DELETE RESTRICT` en todas las tablas hijas del proyecto con valor probatorio SCM (`project_team_role`, `project_methodology`, `project_phase`, `project_milestone`, `project_deliverable`, `github_integration`, `github_event`).
- **Revocación de DELETE para traceflow_app:** El rol de aplicación no posee privilegios `DELETE` sobre entidades históricas ni organizacionales (`SELECT, INSERT, UPDATE` exclusivamente).

### 2.8 Plan Maestro de Implementación Descompuesto en Cinco Hitos
- **INIT-H02:** Organizaciones, proyectos, estados canónicos y persistencia.
- **INIT-H03:** Equipo (DA-06), metodología y planificación.
- **INIT-H04:** Integración GitHub (GitHub App, tokens bajo demanda, webhooks HMAC-SHA256, trazabilidad Git de ECS).
- **INIT-H05:** Interfaz React 19 (asistente de 5 pasos, panel de configuración), salvaguarda SCM `ProjectActiveGuard` y puertas de gobernanza Policy Gate.
- **INIT-H06:** Certificación integral E2E, auditoría con encadenamiento SHA-256 y congelamiento de línea base.

### 2.9 GitHub como Fundamento Operativo del SCM (Dualidad Git y Gobernanza)
- **Separación de Preocupaciones:** GitHub conserva la autoridad sobre el contenido versionado, árboles de directorios, historial de commits, ramas físicas y pull requests. TraceFlow administra la clasificación técnica, autorizaciones colegiadas (CCB), auditoría inmutable SHA-256 y estados formales de los ECS.
- **Identificación y Mapeo de ECS:** Los ECS lógicos (`config_item.code`) se mapean a rutas del repositorio (`file_path`). Sus versiones físicas (`ecs_version`) se asocian a `git_blob_sha` y `git_commit_sha`.
- **Puertas de Gobernanza (Policy Gate):** GitHub Checks API (`TraceFlow SCM / Policy Gate`) bloquea el merge de PRs a ramas protegidas si carecen de RFC admisible, análisis de impacto técnico (`CU-06`) o resoluciones favorables de CCB / QA.
- **Líneas Base Verificables:** Las líneas base congeladas (`traceflow.baseline`) originan Git Tags inmutables (`refs/tags/vX.Y.Z`), correlacionando `git_commit_sha` con los checksums SHA-256 de cada artefacto.
- **Detección Out-of-Band:** Commits no autorizados en ramas rastreadas generan automáticamente un `incident_ticket` (`CAMBIO_NO_AUTORIZADO_GIT`) y alerta en auditoría para regularización o reversión obligatoria (`git revert`).
- **Historial Inmutable de Rutas:** Se crea la entidad `traceflow.config_item_path_history` para trazar renombres (`git mv`), traslados y bajas lógicas (`RETIRED` ante `git rm`), asegurando que la identidad del ECS nunca se destruya.

### 2.10 Remediaciones de Persistencia, Aislamiento y Seguridad (INIT-H02-R)
- **Mínimo Privilegio en Asignaciones:** `traceflow_app` dispone de `SELECT, INSERT, UPDATE` sobre `traceflow.user_project_assignment` revocando estrictamente `DELETE`.
- **Eliminación de Fallbacks Simulados en Producción:** Bloqueo mediante excepción controlada (HTTP 503) ante ausencia de tablas o fallos de conexión en PostgreSQL, restringiendo mocks a `DATABASE_MODE=mock`.
- **Transaccionalidad Atómica:** Operaciones multientidad (organización + miembro + auditoría; proyecto + asignación + auditoría) se ejecutan dentro de bloques transaccionales (`BEGIN ... COMMIT / ROLLBACK`).
- **Sanitización de Datos y Rollback Seguro:** Supresión de RUCs ficticios (`tax_id = NULL`), validación de usuarios en `app_user` e incorporación de salvaguardas en rollback que abortan si existen datos dependientes post-migración, refiriendo a políticas PITR y `pg_restore`.
- **Segregación Estricta de Funciones (SoD):** Requerimiento obligatorio de rol activo `activeRoleId === 'PU-02'` para inicialización institucional y de proyectos, revocando el acceso total al suspender membresías.

### 2.11 Certificación Real de PostgreSQL y Cierre de Persistencia (INIT-H02-V)
- **Certificación Física en PostgreSQL 16 Real:** Ejecución secuencial y limpia de la cadena completa de migraciones históricas (`202611250001`, `202611250002`, seeds, `202611250003` y `202611260001`) sobre motor relacional físico PostgreSQL 16.14 sin DDL simplificado.
- **Auditoría Física Real SHA-256:** Verificación de la función `append_audit_log` con encadenamiento SHA-256 fidedigno utilizando la extensión `pgcrypto` bajo el esquema `extensions`.
- **Aislamiento Obligatorio de Pruebas:** Guardián `assertSafeTestDatabase()` que detecta hosts remotos (`supabase.co`, `pooler.supabase.com`, `amazonaws.com`) y bloquea escrituras con error explícito. Exclusión automática en `vitest.config.ts`.
- **Protección Concurrente del Último OWNER:** Serialización pesimista con bloqueo por fila (`SELECT id ... FOR UPDATE`) en `countActiveOwners` dentro de `DatabaseService.transaction()`.
- **Revocación Efectiva de Acceso a Suspendidos:** Modificación de `RfcsService` para revocar consultas y creación de RFCs (HTTP 403 Forbidden) para usuarios suspendidos en la organización del proyecto.
- **Rollback Seguro sin CASCADE:** Eliminación de borrado en cascada en `202611260001_init_h02_organizations_and_projects_rollback.sql` y parametrización con marcas dinámicas UTC y LSN para Point-In-Time-Recovery (PITR).
- **Cobertura de Certificación:** 15 pruebas físicas en `real-postgres-certification.spec.ts` (100% aprobadas), 77 pruebas backend (`npm test`) y 97 pruebas en prototipo frontend (189 pruebas en verde). Persistencia en Supabase real en pausa bajo Governance Gate.

### 2.12 Cierre Final de Seguridad y Blindaje de Persistencia (INIT-H02-VF)
- **Salvaguarda contra Eliminación Destructiva:** Lista blanca estricta de bases de datos descartables (`ALLOWED_DISPOSABLE_DATABASES`), escape con funciones PostgreSQL `format(%I, %L)` y desacoplamiento de autorización destructiva (`ALLOW_DESTRUCTIVE_DATABASE_RESET=true`).
- **Aislamiento Total de `npm test`:** Ejecución estándar exclusivamente no destructiva; recreación de base de datos restringida al script `npm run test:real-postgres`.
- **Autorización SCM Fail-Closed (`RfcsService`):** Obligatoriedad de validación organizacional, rechazo de proyectos sin organización (DA-02), bloqueo de sesiones de miembros suspendidos (DA-06) y preservación de consulta de RFCs históricas.
- **Rollback Seguro ante Mutaciones de Membresía:** Bloqueo automático del rollback ante cualquier adición o alteración en miembros de la organización semilla.
- **Cobertura Final:** 15 pruebas físicas reales (`test:real-postgres`), 76 pruebas backend (`npm test`) y 97 pruebas en prototipo frontend (188 pruebas en verde). Persistencia en Supabase en pausa bajo Governance Gate.

### 2.13 Cierre Definitivo de Observaciones Residuales de Rollback, Salvaguardas SCM e Introspección (INIT-H02 Residuales)
- **Rollback Coherente con 4 Fundadores Semilla:** Modificación de `202611260001_init_h02_organizations_and_projects_rollback.sql` para reconocer a los 4 fundadores iniciales (`USR-001` como `OWNER ACTIVE`, `USR-002`..`USR-004` como `MEMBER ACTIVE`). Permite la reversión limpia y segura del esquema si no existen mutaciones post-migración, o aborta con `BLOQUEO DE SEGURIDAD` si algún fundador es alterado o existen miembros adicionales.
- **Gobernanza SCM Fail-Closed en Proyectos `ACTIVE` (`DA-04`):** Bloqueo en `RfcsService.createRfc()` que prohíbe crear RFCs sobre proyectos en estado `ACTIVE` en modo PostgreSQL hasta contar con la integración GitHub verificada en `INIT-H04`.
- **Introspección de Socket PostgreSQL y Protección de Pruebas Externas:** Introspección nativa de `inet_server_addr()` (loopback `127.0.0.1`/`::1`) y `datistemplate` en `real-db-helper.ts` antes de cualquier `DROP DATABASE`. Supresión de activación automática de `ALLOW_REMOTE_TEST_DML` en `run-supabase-tests.ts`.
- **Cobertura Física de Certificación:** Ampliación a **18 pruebas físicas en PostgreSQL 16 real** (`test:real-postgres`), 76 pruebas backend (`npm test`) y 97 pruebas en prototipo frontend (**191 pruebas consolidadas en verde**). Persistencia productiva en pausa bajo Governance Gate.

### 2.14 Implementación y Certificación de Equipos, Metodologías y Planificación (Hito INIT-H03)
- **Roles Funcionales de Equipo y DA-06 (`project_team_role`):** Asignación granular con roles canónicos `PU-01` a `PU-07`. Validación relacional en base de datos mediante el disparador `trg_check_project_team_role_org` que rechaza estrictamente cualquier usuario no registrado o sin membresía activa en la organización propietaria del proyecto.
- **Metodología de Desarrollo Parametrizada (`project_methodology`):** Soporte para marcos Scrum (con validación de sprints de 1 a 8 semanas), Kanban, Cascada, Híbrida y UPT Académica con almacenamiento estructurado en `JSONB configuration_params`.
- **Fases Secuenciales y Cronograma (`project_phase`):** Ordenamiento secuencial con unicidad por proyecto y restricción física CHECK `chk_phase_dates` (`end_date >= start_date`).
- **Hitos y Entregables sin Contaminación Cruzada (`project_milestone`, `project_deliverable`):** Disparadores relacionales dedicados `trg_check_milestone_project` y `trg_check_deliverable_project` que impiden referenciar fases o hitos de otros proyectos. Tipificación de entregables y asignación obligatoria de responsables a miembros activos del equipo. Enlace opcional a ECS sin datos ficticios.
- **Asistente Progresivo y Guardado Parcial (`project_setup`):** Soporte atómico de guardado en lote para pasos 2 (Equipo) y 3 (Metodología/Planificación), y guardado/recuperación de borradores mediante `JSONB draft_payload`.
- **Persistencia, Seguridad y Cobertura:** Migración DDL `202611260002` (esquema ampliado a **29 tablas**), script de rollback seguro con salvaguarda de ECS, y mínimo privilegio para `traceflow_app` (SELECT, INSERT, UPDATE; DELETE revocado). **15/15 pruebas físicas en PostgreSQL 16 real** para H03, **18/18 pruebas de regresión física** para H02, **98/98 pruebas unitarias backend**, **97/97 pruebas en prototipo frontend** (**228 pruebas consolidadas en verde**). Persistencia en Supabase productivo en pausa bajo Governance Gate.

### 2.12 Subsanación Final de Aislamiento, Atomicidad y Persistencia (INIT-H03-R)
- **Aislamiento Estricto de Asignaciones (H03-R01):** Todo cambio de estado de rol (`updateTeamRoleStatus`) verifica explícitamente mediante `findTeamRoleById` que la asignación pertenezca al `project_id` de la ruta consultada, bloqueando con `HTTP 403 Forbidden` cualquier mutación cruzada entre proyectos y ejecutando verificación, mutación y auditoría dentro de una única transacción.
- **Preservación Acumulada y No Regresión en el Asistente (H03-R02):** `project_setup.saveSetup` preserva el avance alcanzado mediante `GREATEST($2::integer, wizard_step)` y combina el objeto `draft_payload` mediante el operador JSONB `||`, garantizando que pasos o borradores parciales no sobreescriban banderas completadas previamente (`team_completed`, `methodology_completed`).
- **Atomicidad Transaccional por Lote en Equipo (H03-R03):** El método `saveStep2Team` procesa todas las asignaciones y configuraciones dentro de un único bloque transaccional `db.transaction()`; si un solo integrante incumple validaciones institucionales (`DA-06`), el lote entero ejecuta un `ROLLBACK` total en PostgreSQL sin inserciones parciales huérfanas.
- **Autorización Estricta de Consulta por Proyecto (H03-R04):** Pertenecer a la organización es condición necesaria pero no suficiente. Solo pueden consultar la planificación de un proyecto los administradores globales de la org (`OWNER`, `ADMIN`, `AUDITOR`), el creador/gestor del proyecto (`PU-02`), o usuarios explícitamente asignados al equipo (`assignedProjectIds`, `user_project_assignment`, `project_team_role`); los miembros no asignados son denegados con `HTTP 403 Forbidden`.
- **Salvaguarda Exhaustiva de Rollback (H03-R05):** El script `202611260002_..._rollback.sql` verifica la existencia de datos operativos en las 6 tablas relacionales de H03 y aborta con excepción PITR para prevenir pérdida irreversible de información, admitiendo únicamente reversión si el esquema está limpio o mediante autorización deliberada `SET LOCAL traceflow.allow_force_h03_rollback = 'true'` en entornos descartables de prueba.

### 2.13 Integración Segura de Repositorios GitHub (INIT-H04A)
- **Precondición de Autorización PU-02 Estricta:** Se eliminó cualquier bypass global en `ProjectPlanningService` y `GitHubService` que permitiera a un gestor con rol activo `PU-02` acceder a proyectos donde no esté expresamente asignado en base de datos (`findUserProjectAssignments`, `findTeamRolesByProjectId`), cerrando el vector de fuga multitenant interproyectos.
- **Entidad Relacional `traceflow.github_integration`:** Almacena los metadatos auditables del repositorio (`repo_owner`, `repo_name`, `repo_full_name`, `github_repo_id` numérico estable, `default_branch`, `installation_id`, `visibility`, `permissions` JSONB, `validation_status`, `last_validated_at`, `unlinked_at`, `unlinked_by`).
- **Gobernanza de Repositorio Activo Único (`uq_active_github_repo`):** Índice de unicidad parcial `ON (repo_owner, repo_name) WHERE validation_status != 'UNLINKED'`. Impide que dos proyectos vinculen simultáneamente el mismo repositorio remoto, pero permite su revinculación una vez desvinculado lógicamente.
- **Mínimo Privilegio de Base de Datos:** Concesión exclusiva de `SELECT, INSERT, UPDATE` a `traceflow_app`, con revocación terminante de `DELETE` para preservar la trazabilidad forense.
- **Autenticación con GitHub App y Tokens Efímeros IAT:** Generación de JWT firmados con algoritmo asimétrico `RS256` utilizando la clave RSA privada fuera del repositorio (`GITHUB_APP_PRIVATE_KEY_PATH`). Los Installation Access Tokens (IAT, vida útil 60 minutos) se solicitan a GitHub y se almacenan exclusivamente en caché en memoria (`HttpGitHubApiClient`), garantizando **cero claves privadas y cero tokens de acceso en PostgreSQL o archivos locales**.
- **Desvinculación Lógica sin Efectos Secundarios Remotos:** La acción `POST /api/v1/projects/:id/github/unlink` cambia el estado a `UNLINKED`, registra marca temporal y actor en `unlinked_at` y `unlinked_by`, y actualiza `project_setup.github_completed = false` sin ejecutar mutaciones remotas destructivas sobre GitHub.
- **Contrato de Borrador para Creación de Repositorios:** La acción `POST /create-draft` valida sintácticamente el contrato (nombre según convenciones GitHub, visibilidad, ramas estándar `main`/`develop`) sin aprovisionar repositorios remotos en esta fase.
- **Auditoría Inmutable SHA-256:** Registro atómico de eventos `GITHUB_REPO_LINKED` y `GITHUB_REPO_UNLINKED` en `traceflow.audit_log` con hash encadenado.
- **Salvaguarda de Rollback con PITR:** El script `202611260003_init_h04a_github_integration_rollback.sql` aborta con excepción si detecta integraciones activas validadas, exigiendo Point-In-Time Recovery o autorización explícita `SET LOCAL traceflow.allow_force_h04_rollback = 'true'` en pruebas.

### 2.14 Cierre de Seguridad de GitHub App e Integraciones (INIT-H04A-R)
- **Eliminación del Modo Mock Implícito (H04A-R01):** Prohibición terminante de mocks en PostgreSQL operativo y en producción. Configuración fail-closed mediante `createGitHubApiClient()` que rechaza el arranque o la operación si faltan `GITHUB_APP_ID` o `GITHUB_APP_PRIVATE_KEY`.
- **Aislamiento Multiorganización de Instalaciones (H04A-R02):** Creación de `traceflow.organization_github_installation` (catálogo físico de **31 tablas relacionales**) con permisos mínimos para `traceflow_app` (SELECT, INSERT, UPDATE; DELETE revocado). Los proyectos solo pueden consultar o enlazar instalaciones autorizadas para su propia organización (`organization_id`), con validación estricta del login de la cuenta en GitHub.
- **Unicidad Canónica por Identificador Numérico Inmutable (H04A-R03):** Creación del índice `uq_active_github_repo_id` sobre `github_repo_id` (y auxiliar `uq_active_github_repo_name`), impidiendo que un repositorio vinculado sea enlazado a otro proyecto aun si es renombrado o transferido en GitHub.
- **Sincronización Transaccional de Estado y Degradación (H04A-R04):** `validateIntegrationAccess()` opera dentro de un bloque transaccional atómico: si GitHub reporta permisos insuficientes (push = false), rama inexistente o repositorio inaccesible, `project_setup.github_completed` se conmuta a `false` y se registra el evento `GITHUB_INTEGRATION_DEGRADED` en la bitácora inmutable SHA-256; la recuperación a `true` requiere revalidación exitosa con evento `GITHUB_INTEGRATION_VERIFIED`. Validación de ramas Git reales vía `getBranch()`.
- **Salvaguardas de Rollback con Protección Integral de Datos (H04A-R05):** Bloqueo categórico de reversión en `202611260004` y `202611260003` ante la presencia de registros operativos (incluyendo desvinculados), garantizando la no destrucción de evidencia forense sin Point-In-Time Recovery deliberado.

## 3. Consecuencias y Compensaciones

### Consecuencias Positivas
- **Aislamiento Multitenant Robusto:** Las organizaciones operan de forma segregada; no hay fuga de datos de proyectos entre clientes distintos de ÉXODO S.A.C.
- **Trazabilidad Completa del Código:** Todo cambio tramitado en TraceFlow SCM cuenta con respaldo directo en un repositorio Git verificable.
- **Experiencia de Usuario Guiada:** El asistente previene errores de configuración y permite planificar metodológicamente antes de iniciar el desarrollo.
- **Seguridad Criptográfica:** Cero credenciales expuestas en frontend, bitácora de auditoría ni repositorio de código.
- **Compatibilidad con Código Preexistente:** Se preservan las 21 tablas actuales y las APIs operativas sin interrupción destructiva.

### Consecuencias Negativas / Compensaciones
- **Dependencia de Conectividad Externa:** La activación del proyecto requiere conectividad saliente hacia la API de GitHub (`api.github.com`).
- **Complejidad Adicional de Permisos:** Se debe mantener la coherencia entre el rol institucional (`organization_member`), el rol canónico de seguridad (`PU-01`..`PU-07`) y la asignación en el proyecto.
